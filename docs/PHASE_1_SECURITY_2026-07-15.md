# ProERP Web — تقرير المرحلة 1: المخاطر الأمنية الحرجة

التاريخ: 2026-07-15  
النطاق: الأسرار، Audit Logs، النسخ والاستعادة، أسرار الإنتاج، واجهة الدخول، أخطاء API، رؤوس HTTP، ورفع الملفات.  
حالة قاعدة البيانات: محفوظة دون حذف أو إعادة تهيئة أو migration بنيوية.

## 1. الحالة المؤكدة قبل الإصلاح

- كانت إعدادات الشركة تخزن `smtp_password` في JSON ويستطيع مسار الإعدادات دمجه في الاستجابة.
- كان Audit Log يسلسل الكائن كاملًا دون تنقيح مركزي للأسرار.
- كانت نسخة SQLite تنسخ ملف `.db` مباشرة، ولذلك لم تكن تضمن تضمين معاملات WAL الملتزم بها.
- كانت الاستعادة تستخدم محتوى ZIP دون سياسة صارمة للمسارات، الحجم، الأنواع، أو سلامة قاعدة البيانات.
- كان رفع الصور يثق في MIME المعلن ولا يفحص الامتداد أو التوقيع الثنائي.
- لم يكن التشغيل في production يرفض `SECRET_KEY` الافتراضي.
- لم تكن هناك CSP، وكانت واجهة الدخول تعرض معلومات الحساب الأولي في جميع البيئات.
- لم توجد اختبارات أمنية آلية في المستودع.

## 2. الإصلاحات المنفذة

### فصل الأسرار وتنقيح التدقيق

- أُنشئت طبقة مركزية للإعدادات تفصل القيم العامة عن الأسرار؛ API يعيد `smtp_password_configured` فقط.
- نُقل سر SMTP الحالي من `company_settings.json` إلى `backend/.env` بأداة ذرّية لا تطبع القيمة. لم يتم تدوير السر أو تغييره.
- كل حفظ جديد للإعدادات يزيل حقول password/secret/token/passphrase/API key بدل تخزينها.
- أصبح تنقيح الأسرار في Audit Log متداخلًا وموحدًا.
- نُقحت السجلات التاريخية وأُعيد حساب `previous_hash` و`log_hash` لكل السلسلة. تمت معالجة 73 سجلًا وتنقيح 6 سجلات؛ فحص السلسلة بعد الترحيل ناجح.

### النسخ والاستعادة

- أصبحت نسخة SQLite تستخدم `sqlite3.Connection.backup()` لتضمين بيانات WAL الملتزم بها.
- الاستعادة تفرض حدًا لحجم الملف، وعدد الأعضاء، والحجم بعد فك الضغط، وحجم كل عضو، ونسبة ضغط مشبوهة.
- تُرفض المسارات المطلقة و`..` وbackslash والروابط الرمزية والمحتويات غير المدرجة في القائمة البيضاء.
- يُشترط ملف `proerp.db` واحد، ثم `integrity_check` والجداول الأساسية قبل إنشاء نقطة الأمان وتعديل البيانات.
- الإعدادات المستعادة تمر بطبقة التخزين الآمنة، وuploads المستعادة تقبل JPG/PNG/WebP فقط.
- النسخة ZIP غير مشفرة تحمل تحذيرًا واضحًا؛ `.erpenc` هي الصيغة الموصى بها خارج الجهاز.

### Runtime وHTTP وواجهة المستخدم

- production يرفض الإقلاع إذا كان `SECRET_KEY` افتراضيًا أو أقصر من 32 حرفًا.
- أضيفت CSP وCOOP و`nosniff` وسياسات frame/referrer/permissions، مع HSTS عند HTTPS.
- لم تعد حزمة واجهة production تحتوي كلمة المرور الافتراضية أو تعرض بيانات دخول افتراضية.
- واجهة SMTP تعرض حالة الضبط فقط، وواجهة النسخ تعرض تحذير ZIP غير المشفر.
- أخطاء SMTP والأخطاء الداخلية في جرد المخزون لا تعيد نص الاستثناء الخام للمستخدم.

### رفع الملفات

- CSV: امتداد وMIME وحجم 5 MB وحد 10,000 سطر.
- الصور: امتداد متوافق مع MIME، حد 2 MB، وتوقيع ثنائي حقيقي لـJPG/PNG/WebP.
- SVG والملفات التنفيذية والمحتوى المتنكر بصورة مرفوضة قبل الكتابة أو تعديل المنتج.

## 5. المخاطر والقيود المتبقية

- لم يتم تدوير كلمة مرور SMTP؛ التدوير يحتاج تغييرًا عند مزود البريد ثم تحديث `SMTP_PASSWORD`، ويجب تنفيذه بموافقة المستخدم.
- النسخ القديمة التي سبقت هذه المرحلة قد تحتوي إعداد SMTP تاريخيًا؛ يجب حمايتها ثم حذفها فقط بعد اعتماد نسخة مشفرة حديثة وسياسة retention، وليس تلقائيًا في هذه المرحلة.
- ZIP المحلي يبقى غير مشفر عن قصد مع تحذير واضح؛ يلزم اختيار `.erpenc` للتخزين الخارجي.
- سياسة CORS الحالية تشمل نطاق Cloudflare المؤقت الواسع؛ تضييق الثقة حسب بيئة النشر موضوع production hardening لاحق.
- rate limiting والجلسات وMFA/Firebase وtoken revocation تقع ضمن المرحلة 2.
- لا يوجد Git صالح في مساحة العمل، لذلك rollback يعتمد على النسخة الاحتياطية ونسخ الملفات اليدوية بدل commit موثوق.

## 7. Rollback

1. أوقف Backend فقط.
2. أعد ملفات المصدر يدويًا من نسخة ما قبل المرحلة؛ لا يوجد Git صالح حاليًا.
3. عند الحاجة للبيانات، استعد النسخة الأساسية المتحققة في تقرير المرحلة 0 عبر بيئة اختبار أولًا.
4. إذا أُعيد كود SMTP القديم، يجب إعادة الحقل يدويًا من مدير الأسرار؛ لا تُنسخ القيمة إلى السجلات أو التوثيق.
5. شغّل `compileall` وbuild و`/health` ثم اختبر settings وbackup قبل إعادة الخدمة.

لا يُنصح بالتراجع عن تنقيح الأسرار أو حماية ZIP/uploads إلا لمعالجة عطل طارئ موثق.
