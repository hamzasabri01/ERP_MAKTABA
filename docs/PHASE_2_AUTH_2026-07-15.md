# ProERP Web — تقرير المرحلة 2: المصادقة والجلسات

التاريخ: 2026-07-15  
النطاق: Local/Firebase login، MFA، كلمات المرور، access/refresh sessions، CSRF، recovery، rate limiting، وعناوين proxy.  
النسخة قبل migration: `backend/backups/proerp-backup-20260715-154439.zip`، CRC وSQLite integrity ناجحان والأعداد مطابقة.

## 1. المشكلات المؤكدة قبل الإصلاح

- كان JWT صالحًا 12 ساعة ومحفوظًا دائمًا في `localStorage`.
- كان Firebase يصدر جلسة ProERP مباشرة ويتجاوز MFA المفعّل على المستخدم.
- تغيير كلمة المرور لا يطلب الكلمة الحالية ولا يبطل التوكنات القديمة.
- logout يمسح المتصفح فقط دون revocation في Backend.
- لم توجد refresh rotation أو recovery codes أو آلية استعادة مدير محلية موثقة.
- كان TOTP secret مخزنًا نصًا واضحًا.
- rate limit داخل dict لذا لا يعمل بصورة مشتركة بين workers.
- كان التطبيق وUvicorn قادرين على الثقة بـ`X-Forwarded-For` من مصدر غير مصرح.
- كانت قاعدة البيانات تحتوي 5 مستخدمين نشطين ومستخدم MFA واحد يجب الحفاظ عليه.

## 2. التغييرات المنفذة

### الجلسات والتوكنات

- access token افتراضي 15 دقيقة وموجود في ذاكرة JavaScript فقط؛ لا token ولا user session داخل `localStorage`.
- refresh token لمدة 7 أيام داخل Cookie `HttpOnly`، مع rotation في كل refresh ورفض إعادة استخدام القديم.
- CSRF double-submit للـrefresh/logout، مع bootstrap endpoint لدعم frontend منفصل موثوق عبر CORS.
- `SameSite=strict` افتراضيًا؛ يمكن ضبط `none` فقط مع Secure cookies لحالة Firebase frontend منفصل.
- `session_version` داخل المستخدم والتوكن؛ logout وتغيير كلمة المرور وreset المدير وتغيير MFA الحساس يبطل الجلسات السابقة.
- السياسة الحالية تسمح بجلسة refresh قابلة للتجديد واحدة لكل مستخدم؛ تسجيل دخول جديد يستبدل refresh السابق، بينما ينتهي access السابق خلال 15 دقيقة كحد أقصى أو فور زيادة `session_version`.

### كلمة المرور والاسترداد

- أزيل password من `PUT /auth/me`، وأضيف `POST /auth/change-password` الذي يطلب الحالية ويطبق strength validation ثم يبطل كل الجلسات.
- reset كلمة المرور من إدارة المستخدمين وتعطيل المستخدم يرفعان `session_version`.
- أضيفت أداة استعادة مدير محلية تفاعلية، dry-run افتراضيًا، تنشئ backup، لا تقبل password في CLI، وتسجل العملية.
- قواعد البيانات الجديدة لا تنشئ كلمة مرور مدير افتراضية؛ يلزم `INITIAL_ADMIN_PASSWORD` في البيئة لأول تشغيل فقط.

### MFA وFirebase

- Local وFirebase يعيدان challenge MFA نفسه إن كان MFA مفعّلًا.
- TOTP secret مشفر في قاعدة البيانات بمفتاح مشتق ومفصول نطاقيًا من `SECRET_KEY`.
- عند التفعيل تُولد 10 recovery codes وتُعرض مرة واحدة؛ المخزن يحتوي HMAC hashes فقط.
- كل recovery code يستهلك مرة واحدة، ويمكن إعادة توليد المجموعة بعد password + TOTP.
- تفعيل/تعطيل MFA يدور الجلسة ويبطل access/refresh السابقين دون إخراج المستخدم من التدفق الحالي.

### Rate limiting وproxy trust

- أضيف جدول `auth_rate_limit_attempts` وفهرس مركب؛ محاولات login وFirebase وMFA وrefresh مشتركة عبر workers.
- مفاتيح limiter مخزنة hashes بدل username/IP خام.
- التطبيق لا يفسر forwarded headers إلا إذا كان المصدر ضمن `TRUSTED_PROXY_IPS`.
- التشغيل المحلي يضيف `--no-proxy-headers` إلى Uvicorn؛ Docker يقيد `--forwarded-allow-ips` إلى شبكة proxy المعلنة.

## 6. المخاطر والقيود المتبقية

- كل الجلسات القديمة التي لا تحتوي `session_version` أصبحت غير صالحة عمدًا؛ يلزم تسجيل الدخول مجددًا.
- المستخدم الذي كان MFA مفعّلًا قبل المرحلة لا يملك recovery codes قديمة؛ يمكنه توليدها من الملف الشخصي بعد password + TOTP.
- `SECRET_KEY` يحمي JWT وتشفير MFA وrecovery hashes؛ لا يجب تدويره مباشرة دون re-key migration، وإلا تتعذر قراءة TOTP الحالية.
- frontend منفصل عبر نطاق آخر يعتمد على third-party cookie policy للمتصفح؛ reverse proxy same-origin هو الخيار الأكثر موثوقية.
- سياسة refresh الحالية one-renewable-session-per-user آمنة وبسيطة لكنها تحد تعدد الأجهزة؛ جدول جلسات متعدد الأجهزة يمكن إضافته لاحقًا إذا أصبح مطلبًا.
- تحذيرات Python الخاصة بـ`datetime.utcnow()` ما زالت موجودة في الكود القديم والجديد؛ الانتقال إلى UTC-aware datetimes مسجل كتحسين لاحق لتوحيد timezone.
- لا يوجد Git صالح في مساحة العمل؛ rollback المصدر يدوي إضافة إلى migration/backup.

## 8. Rollback

1. أوقف Backend.
2. شغّل من `backend`: `..\.venv\Scripts\python.exe migrations\phase2_auth_sessions.py downgrade`؛ يفك TOTP secret ثم يحذف أعمدة/جدول المرحلة.
3. أعد ملفات المصدر السابقة يدويًا، لأن Git غير صالح.
4. البديل عند حادث بيانات: استعد نسخة ما قبل المرحلة `proerp-backup-20260715-154439.zip` أولًا في بيئة اختبار.
5. امسح Cookies الخاصة بالتطبيق من المتصفح ثم شغّل compile/tests/build وhealth/login.

الـdowngrade أو استعادة النسخة القديمة يعيدان نموذج الجلسة الضعيف، لذلك يستخدمان فقط للاستجابة لحادث موثق.
